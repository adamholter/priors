# Data, scrapers and index math

## The contract

`src/data/types.ts` defines everything: `Snapshot`, `Model`, `Variant`, `Benchmark`, `Observation`, `RawRow`, `Source`. Read it first.

- A snapshot is one gzipped JSON file per day in `data/snapshots/<date>.json.gz`, plus `latest.json.gz`. They are committed: the repo is the archive.
- `src/data/load.ts` loads a snapshot by date or the latest, passing it through `canonical-snapshot.ts` (repairs identities in older snapshots) and `share-strings.ts` (every observation's ids, source pages and scrape times point at one shared copy: 40% less memory, 25 MB to 15 MB per snapshot). It keeps the six most recently used snapshots in memory, the live one included; older dated files are read again when asked for.
- `src/data/columns.ts` lays a snapshot out for the engine (`columnsOf`, built once per snapshot object and rebuilt if a list is replaced or grows): benchmark and variant ids interned to integers, `at[variant * nb + benchmark]` pointing at a row, and each row's value, flags and harness in typed arrays. When a cell has several plain measurements under different harnesses (ARC's Provider Adapter, Terminal-Bench agents), the best one is the cell's value, whatever order the source listed them in. `observationsOf` gives one benchmark's observations, for code reading a few hundred rows of plan or task data.
- `/api/snapshot?view=core&packed=2` is what pages fetch: `coreSnapshot` (no published intervals or ranks, which only benchmark pages show) as columns (`src/data/packed-snapshot.ts`: benchmark, variant and page named by index into shared lists, other fields as sparse columns with repeated strings kept once), about 2.6 MB of JSON against 8.9 MB plain. `packed=1` and no parameter return plain `clientSnapshot` JSON, for tabs on an older bundle and outside readers.
- `src/data/client-snapshot.ts` trims a snapshot for the browser (no scrape times, notes or raw details; source-model metadata cut to the fields the browser reads).
- The pages that calculate (builder, compare, 3D, and model pages when a visitor needs more than the standard rankings) load that dataset in the browser through `src/components/use-core-snapshot.ts`: one fetch and one parsed copy per tab, shared as the visitor moves between them, refreshed after five minutes. Never pass a whole snapshot as a server component's prop: it is serialized into the HTML (a model page was 21 MB). `scripts/verify/memory.mjs` measures each page's heap, DOM and bytes against a running build.

## Model identity

`src/data/normalize.ts` turns a source's model label into a canonical model id and reasoning effort.

- Regex families plus exact `ALIASES`. Unknown labels are excluded, never guessed.
- `src/data/model-labels.ts` lists exact spellings the families cannot read, each checked by hand, with a release date for a model no source dates yet. Unnamed stealth models, routers, products and dated checkpoints stay out, so they stay unknown.
- A variant (model + reasoning effort) is the ranked unit. When a source gives no effort, the row goes to the model's highest known effort.
- `none`, `minimal` and `low` are distinct efforts. Explicit model sizes (Qwen 27B versus 35B-A3B), Instant variants and dated DeepSeek revisions stay distinct too.
- `preview` is normally noise in a label, because a preview and its release are the same model. Hy4 is the exception: `hy-4-preview` and `hy-4` differ in weights, vision and scores.
- A generation number is a new model: `Inkling 2 Small` (594B) is `inkling-2-small`, never the original 975B `inkling`.
- Vals lists Meta's models without the brand: `Wonder` and `Wonder Full` are `aa-muse-wonder` and `aa-muse-wonder-full` (exact labels in `VALS_PUBLISHED_MODELS`).
- The catalog keeps models and variants a source stops listing (`retain-catalog.ts`). A retained model or configuration with no rows whose labels all resolve to another current model is a trace of a moved label and is dropped, so a split (Inkling 2 Small off Inkling, Carbon off Argon) leaves no stale configuration or orphan twin behind.
- `preview` stays a distinct model for o1 too: `o1-preview` (Sept 2024) is not `o1` (Dec 2024).
- A full DeepSeek date names a checkpoint (`deepseek-v4.1-flash-20261017` is `deepseek-v4.1-flash-1017`); the launch checkpoint keeps the bare id (`FIRST_CHECKPOINT`: V4.1 Flash launched as 0910).
- A thinking budget in tokens is a setting, never a version (`claude-3-7-sonnet_thinking_1024` is Sonnet 3.7). LLM Chess keeps each budget as its own configuration, as ARC does, and the no-budget Claude row is thinking off.
- **Release dates:** a source's own record for exactly that model (AA's canonical record, not a dated configuration) beats a leaderboard row's date; otherwise the first source's date stays (`applyDateHint`). Then overrides and OpenRouter fill the gaps. `RELEASE_DATE_PINNED` beats every source, each with its reason (Mistral Large 4: public on the API Oct 6, AA dates its Oct 29 open weights). Catalog retention drops a model's old date when one of its labels moved to another model, and a carried row follows its source record to its current variant. A carried row keeps only its first "carried from" date.
- Codenamed tiers are distinct models: GPT's Sol, Luna, Terra and Astra, and Gemini 4's Carbon (`gemini-4-carbon`). Gemini 4 Argon came first, so it keeps the bare `gemini-4` id.
- A label that is not one released model is unknown, never filed under the nearest name: a router (`gpt-6-auto (astra+luna)` sends each task to Astra or Luna, and read as a bare GPT-6) and an unreleased `Early` build (`Qwen-4-27B-Early` took the id the release will get).
- Lab colors live in `LABS` in `normalize.ts`: same lab, same color everywhere.
- Regression corpus: `scripts/benchmarks/` (`npm run benchmark:identity`, also run by Vitest). For a new parsing defect, add the source label and the independently reviewed identity to `fixtures/identity-cases.json`. Never edit expected groups to match the parser.

## Descriptions and categories

What a reader sees about a benchmark is written in one place, `src/data/catalog/` (one file per source family, keyed by benchmark id, with pattern rules for families such as Arena's slices and MathArena's dated editions). A scraper says where the numbers come from; the catalog says what they mean.

- **Descriptions** open with what the model is asked to do, in plain words, then how the number is scored, then any caveat. No "Name:" opening, no em dashes, no unexplained jargon (say "share solved on the first try", not "pass@1"). State only what the publisher's page or paper states.
- **Categories** are in `src/data/categories.ts`. A benchmark can sit in several (`categories`, main one first); `category` is the main one, which groups it in pickers and on charts. The directory's filter, search and the model page's "By category" radar count it in all of them. Read categories through `categoriesOf` and `categoryName`: snapshots saved before November 12, 2026 carry the old names (`economics`, `instruction`), which `normalizeCategory` maps.
- The catalog is applied twice: at the end of the scrape build, so the published data carries it, and when the site loads any snapshot (`parseSnapshot`), so an archived day reads like the live one and a catalog edit is live on deploy. Applying it twice changes nothing.
- A benchmark with no entry keeps its source's description and category, and the build log names it (`catalog: no entry for …`). A new source needs a catalog entry in the same change.

## Scrapers

`scripts/scrape/build.ts` runs every file in `scripts/scrape/sources/`, normalizes the rows and writes the snapshot. Raw payloads go to `data/raw/` (gitignored).

```
npm run scrape -- --date YYYY-MM-DD [--only aa,openrouter]
```

A full run takes 2 to 3 minutes (some sources use headless Chromium). A partial `--only` run keeps the other sources' rows and observation notes unchanged, even when their previous scrape failed, and seeds effort attribution from the previous snapshot.

To add a source, copy `sources/_template.ts`. Its header lists the rules: discover rows live, prefer structured payloads over DOM scraping, emit the label exactly as the site shows it, put a cost in `costUsd` only when the site reports measured run cost, save every parsed payload in `raw`.

### Config-only boards

Most leaderboards need no scraper file. `scripts/scrape/boards/configs.ts` lists boards that one of four generic readers (`boards/readers.ts`) can read:

- `ariaLabel`: chart text in an `aria-label` ("Fable 5.2: 82.2%", "Dots 75.9%", "GPT-6 Astra: low 76.7% at $0.200 per question, medium ..."). `match` picks the label, `after` drops a leading sentence (agent products, baselines). A cost is read only when the text says it is per question, task or run, never a token price.
- `nextData`: JSON in `<script id="__NEXT_DATA__">` (or another JSON script, `script: "<id>"`). `rows` is a path to the row array; `label`, `value`, `effort`, `ciHalf` (or `ciLow`/`ciHigh`), `cost` and `details` are paths inside a row. Paths are dot-separated keys, `[n]` for an index and `[key=value]` for the element whose `key` is `value`: `props.pageProps.benchmarks[leaderboardKey=open-world-engineer-leaderboard].globalLeaderboard`, `passScores[pass=mean-8].score`. An object of rows keyed by model reads as rows with the key in `$key`.
- `json`: the same selection over a JSON endpoint (`fetch`), with `url` the public page.
- `table`: an HTML `<table>` by index or by text in one of its headers, columns by header name (exact, else the first header containing it). The header is the last `<thead>` row, so group headers with colspans are skipped.

A config also carries the benchmark record (`id`, `name`, `unit`, `category`, `minRows`, ...), label fixes (`labelMap`, then `labelPrefix` for Claude models written without the family), `skip` for labels that are not models, `scale` for 0 to 1 fractions, and `browser: true` for a board drawn in the browser. `sources/boards.ts` exports one Source per config, under `sourceId` (default the benchmark id), and `build.ts` runs a file's `sources` export in place of its default. So each board fails, is reported, carries forward and takes `--only <id>` on its own, and `--only boards` runs them all. Company Agent Bench and OWE-Bench (source id `mercor-apex`) run this way; their rows matched the old scrapers exactly.

To add one, run `npm run board:try -- <url>`. With no reader it lists candidates (aria-labels, JSON scripts, tables, and JSON files the page links), each with its options, row count, first rows, and what `normalizeLabel` makes of every label (model id and effort, UNKNOWN, or a model the current snapshot lacks), then prints a config for the best one and a catalog stub. `--reader <name>` with its options (`--rows`, `--label`, `--value`, `--table`, `--match`, `--details name=path,...`) runs just that reader; `--browser` renders the page first; `--config <id>` checks a config already in the file. Paste the config, write the catalog entry (required: the config test fails without one), and run `npx vitest run scripts/scrape src/data`. A board none of the readers can read still gets a hand-written source.

Every benchmark comes from a live scraper. No frozen datasets are merged at load time. `liveBenchmarkId` in `src/lib/url.ts` maps the ids of a removed September 2026 import (`real-index:*`) in old shared links to the live benchmarks.

### Launch figures for new models

**AA speed (Performance Benchmarking v3.0.0).** From the Nov 4, 2026 snapshot, `aa-output-speed` and `aa-ttft` read `headline` (full-duration speed, averaged across workloads over 5 days, endpoint failures count as 0); before that, `timescaleData` medians. AA's time per task (`details.estimatedDecodeSecondsPerTask`, an old name kept so older snapshots still read) is computed, tokens divided by that speed: it matches `intelligenceIndexOutputTokensPerTask.output / headline.outputSpeed` exactly, is not timed, and leaves out tool time. `src/data/series-breaks.ts` lists such method changes: `/history` marks them when the index weights that benchmark, benchmark pages note them, and captions change with the snapshot's date. Add an entry whenever a publisher redefines a number.

**API default effort.** `Variant.apiDefaultEffort` comes from `defaultEffortHighlightedIds` on AA's home page. AA lists leading models only, so unset does not mean a variant is not the default. **Endpoint errors.** `aa-endpoint-error-rate` reads `/leaderboards/providers`, only for models whose speed comes from the lab's own API, as that is one published endpoint. A model reported as a median across providers has no row. The per-endpoint numbers are in the raw `endpoint-error-rates.json`.

`scripts/scrape/launch-claims.ts` holds the scores a lab publishes in its launch table, for boards that have not run the new model yet. Before adding a row, compare the reference models in the lab's table with the board's own values: if they differ, it is a different harness or version, so leave the row out. Each entry maps the table's rows to benchmark ids Priors already tracks (same version and harness as the board; rows that differ or that nothing tracks are left out). `build.ts` adds a score only while the board's own data has no result for that model at any effort, so the board's number replaces it the day it appears, whatever it says. A lab that charts several efforts gets one entry per effort (GPT-6.2 Astra and Sol: low to max, read from the post's chart data); a claim carried from the last run is skipped by variant and benchmark, so the efforts don't hide each other. `fillEfforts` on a claim makes it step aside per effort instead of per board, for a board that publishes a model's efforts one at a time when the lab's figure is the board's own (GPT-6.2 Sol's cost per task: AA listed max first; low to xhigh come from OpenAI's chart, which is AA's cost to the cent). ### Subscription cost

`sources/realapipricing.ts` reads `derived/points.json` from github.com/FeiZhuLulu/real-api-pricing into the proxy benchmark `subscription-token-price`: plan fee divided by monthly tokens on the plan with the model's biggest subsidy, lowest share of API price among the lab's own plans and resellers or harnesses alike (OpenCode Go, Command Code, Droid, Ollama). The build then moves each row to the model's best common plan (`src/data/plan-defaults.ts`, below), so the scraper's pick only stands where no common plan sells the model. Plans closed to new customers count only when nothing else is sold, a `low`-confidence row counts only when it is the lab's own and the lab has nothing surer, and plans within 0.5% tie toward the surer figure and then the lower fee. `sources/subscription-overrides.ts` holds curated figures read from a plan page that states its allowance in dollars (Muse Wonder on Command Code Max at 1.5×; Gemini 4 Argon's OpenCode Go promo figure was retired on 2026-10-28 once Real API Pricing measured Google AI Pro, whose slug `gemini-4-argon` maps to Priors' `gemini-4` through `PRIORS_IDS` in `realapipricing.ts`). They carry `ratio` directly, replace any computed row, and need about 80% confidence and a checked date. **Token mix.** `sources/slopalytics.ts` puts each model's measured mix in `t3-usage-share`'s `details.tokenMix`: its shares of all tokens (cache read, fresh input, cache write, output) over the export's last 7 days, on the harness with the most usage, with other measurable harnesses in `byHarness`. It needs 1B tokens and 1,000 turns in the window; 100B makes it `high` confidence, otherwise `medium`. It refreshes with every scrape. `tokenPrice` blends list prices at that mix, falling back to the plan's assumed mix, and the model page shows the result with the dates and confidence. A plan's share of API price deliberately does not use it: the plan's token price was converted at the plan's mix, and an allowance spent at list prices gives the same share at any mix, so cost per task doesn't move. The Codex-limits estimate compares two models' prices, which does depend on the mix, so it uses each model's measured mix. The mix describes T3 Code users only. It can't say why a mix changed: Codex's permanent caching has no known launch date in this data.

**Limit resets.** A lab now and then refills everyone's weekly allowance early, which is extra usage on top of the plan. `scripts/scrape/plan-resets.ts` keeps each lab's reset history in `snapshot.planResets` (not a benchmark: it prices plans, never ranks): OpenAI from OpenTheRank's Codex reset tracker (opentherank.com/codex-reset; Tibo's, every reset a `cx-stamp` element with an ISO time and type), Anthropic from claude-resets.com's `data/resets.json` (CC BY 4.0; unofficial, entries link the ClaudeDevs posts; its `policy` entries are limit changes, not resets), and Google (Antigravity's Gemini quota) from `GEMINI_RESETS`, kept by hand because no tracker covers it: add each all-user reset Google announces, with the post. The first is Thanksgiving, 2026-11-26 07:17 UTC (Varun Mohan's post at 07:19; a second post that day, x.com/ckbrox13/status/2125942944742138131, quotes it and refilled nothing more, so it is one reset); a weekly-quota log showed 32.5% used drop to 0 at 07:17 and the next reset date move to 7 days after the next use. Each Antigravity subscriber's week starts at their own first use and a reset restarts it, so the reset lands at a random point in each subscriber's week: the `rolling` clock values it at half an allowance. `build.ts` runs it after the free tiers, always carries the last history forward, and replaces a lab only when its source was read: a changed page throws instead of reading as "no resets". `src/data/plan-resets.ts` turns it into the adjustment, over the 30 days before the snapshot (`generatedAt`). The two labs' resets do different things to the weekly clock, so they are valued differently: Claude's "weekly limits still reset on their usual day and time" (Claude Help Center, "What is a limit reset?"), so each reset is a whole extra allowance (+1 week); an OpenAI reset moves the weekly reset date and the next one comes 7 days later (Codex help), so it replaces the rest of the old week and adds only 1 - x of an allowance, x being how far into its week the reset landed (the previous reset, then a 7-day clock from it, so it is worked out from the real reset times). 12 Codex resets in the last 30 days, 1 to 5 days apart, add 7.5 weeks. Both assume the plan prices' own premise, that the subscriber spends every allowance. **Banked resets count too** (since 2026-11-13, Adam): each once, on the day it was granted. The source records grants, never when anyone applied one, so nothing is counted twice; a banked reset is an extra allowance on top of the regular ones. A full Claude banked reset is +1 week like a regular one; an OpenAI banked reset is +0.5 (applying it restarts the week at a time Priors cannot see) and does not move the clock the regular resets are measured on; a `both` event is a regular reset plus a banked one. Claude's **Fable 5.2 grant** (2026-11-09, `refills: "fable"`, read from the entry's note) restores the Fable usage on the weekly meter (Fable stops at half the week, so at full use half an allowance) and refills Fable's own cap: +0.5 week for other Claude models, +1 Fable allowance for Fable 5.2 (`resetBoostFor`), for each grant held. Accounts hold 1 to 3 by paid tenure (Max/Ultra 1 under 6 months, 2 at 6 to 12, 3 over 12; Pro and standard Team 1); no source says how many a typical account holds, so Priors assumes 1, the number every eligible account got, and the visitor can set 0 to 3 ("Fable resets you hold", `fableResets`, `fresets=` in links). Resets only some users got are not counted. A lab's plan share of API price is divided by `1 + extraWeeks / (30/7)`: 2.75× for OpenAI today. It is **off by default** (Adam, 2026-10-28): the engine applies it on the subscription basis only when turned on (`config.planResets === true`; "Count limit resets" under Advanced in chart settings, remembered per browser once turned on (`priors:plan-resets` = `on`, `src/lib/plan-resets-pref.ts`; applies to every page until turned back off), `resets=on` in links, `planResets: true` in stored configs and MCP; older configs' `planResets: false` and links' `resets=off` read as the default), notes it in the cost source ("with 12 limit resets in 30 days"), and the settings panel says what is counted. Claude's plan, at the time of writing, has had no regular reset for over 30 days, so its price is unchanged.

**Merged labels.** A family rule that matches `SWE-2` and ignores `Flash` files a new model under an old one. `scripts/scrape/label-collisions.ts` reports it two ways: `labelCollisions`, a row the build's keep-first dedupe drops because a label with different tier words holds it (SWE-2 Flash's max row), and `swallowedTiers`, a label naming a tier its model does not have, which catches it before any row collides. **Free tiers and OpenCode Go.** A model free today gets a ratio 0 row, and its paid row rides along as `details.paid`. **Speed tiers.** `scripts/scrape/speed-tiers.ts` keeps each model's Flex, Fast and Ultrafast in `snapshot.speedTiers` (not a benchmark: same model, same scores). `rates`: tier price and measured speed against that model's standard. The Devin Max GPT-6.2 rows measure Cognition's own quota and are unaffected.

**Default plan.** Each model's row is on its best common plan, not the single biggest subsidy, which put models on plans nobody uses (Command Code GOAT) and spread one lab's models over several plans (Adam, 2026-11-19; it replaced the biggest-subsidy default of 2026-11-18). `withCommonDefaults` in `src/data/plan-defaults.ts` runs in the snapshot build after T3 costs (log line `PLAN_DEFAULTS`). Common: the lab's own current consumer plans (no legacy, existing-subscriber, peak or mixed, team, student or China-only rows where a global one exists, such as MiniMax's) plus resellers people use (OpenCode Go, Ollama Pro and Max, Cursor). Each lab gets one default: the common plan with the biggest subsidy for its flagship (its newest model with plan data, the priciest on a tie; the cheaper fee when two plans give the same subsidy, so ChatGPT Pro 10x over Pro 20x). A model takes it when it is within 10% of its own best common plan, else its own best common plan (Kimi K3 keeps Kimi Max at 13x rather than OpenCode Go at 1.5x), then any plan but Command Code. A model sold only on Command Code gets no row and is priced at the API. Curated and assumed rows keep their plan. Running it again changes nothing, so a partial scrape keeps it.

**Which plan.** Each model is priced at its default plan unless the viewer picks one for its lab under Data → Subscription plans in a cost chart's settings (a row per lab with more than one plan in the data, from `subscriptionPlanOptions`: the lab's logo, the plan its models are on and that plan's subsidy as a line, opening to every plan in that lab's rows' `plans` list, the biggest subsidy first; each plan's figure is the median over the lab's models, `labPlanMultiples`). `config.subscriptionPlans` maps lab id to plan name; `subscriptionPrices(snapshot, chosen)` then uses that plan's measured token price for every model of the lab that has it, and its default plan for any that does not. A model assumed to match another (`sameAs`) follows the plan that model is priced at. The choice is remembered per browser (`priors:subscription-plans`, `src/lib/subscription-plans-pref.ts`; a link's or page's choice for a lab wins), carried in links as `plans=lab:Plan%20name,...` (also in chart links' `hv`), and stored on saved pages (Convex validator `subscriptionPlans`).

Subscription pricing is the default: `IndexConfig.costBasis` unset means subscription (`effectiveBasis` in `src/data/subscription.ts`); only an explicit `"api"` is stored (URL `costbasis=api`, the Pricing toggle in the cost chart's settings). It multiplies measured cost per task by that share, so a free tier costs $0. Log cost axes have no 0: `costChart.points` puts free models a step left of the cheapest paid cost (`freeFloor`, a quarter of it) with `free: true`, tooltips and bar labels read "free", and the scatter draws a dashed "free" line there. Models without plan data keep API cost. It is a lower bound, because it assumes the full allowance is used. The toggle only shows when the snapshot has the benchmark.

### Availability and plan subsidies

`modelAvailability` (`src/lib/model-availability.ts`) feeds the Availability section of a model page. The server sends it with the page, so it does not change with a visitor's ranking and stays out of the browser dataset.

- **Providers** (`src/data/providers.ts`). The `openrouter` source stores each model's endpoints on its `openrouter-providers` row (`details.endpoints`): one row per provider, the cheapest endpoint that is not a flex, spot or batch tier. Rows open and close with the height animation in `plan-subsidies.css`, which stops while searching and under reduced motion. Logos are in `public/logos`. ### Rank stability

`/api/rank-stability?r=general|aa[&model=<id>]` re-ranks a standard ranking 120 times with every weight multiplied by a log-normal factor (sigma 0.36, fixed seed) and returns each model's 10th, 50th and 90th percentile rank (`src/lib/rank-stability.ts`). No page draws it. A model page requests its own row after load, so it can be read from the network tab.

### Open weights

`Model.openWeights` says whether a model's weights can be downloaded (any license); `paramsB` and `activeParamsB` hold parameter counts in billions when a source publishes them. `src/data/open-weights.ts` sets them at scrape time, from the most to the least trustworthy: `CHECKED_WEIGHTS` (repos checked by hand), Artificial Analysis's `isOpenWeights` in each variant's source metadata, flags other sources return in `modelFlags` (Epoch ECI's accessibility group, Benchmark Heaven), then `FAMILY_RULES` for families whose status never varies. Unknown stays undefined, which is not the same as closed. The build logs `OPEN_WEIGHTS n open, n closed, n unknown`. `/api/history` fills the flag on older snapshots from today's models, since a model's weights don't change. Charts: the history page's "Open vs closed" colouring and best-by-weights chart, and the assistant's `weights` filter.

### New benchmark versions

A source that can read the publisher's version label sets `version` on its benchmark and keeps one id. When the label changes from what the last snapshot stored (GameFeel v1.4 to v1.5), the build freezes the old scores under the old id and files the new version as `<id>-v<version>` with `versionPolicy: fresh` (`scripts/scrape/version-splits.ts`). The scrape writes the frozen copy to `data/frozen-versions/` and logs a NEW_BENCHMARK line; commit it to `scripts/scrape/sources/frozen/versions/`. A version the source never labeled can be seeded there by hand from an old raw file.

## Index math

`src/engine/index.ts`. Tests in `index.test.ts`. The engine works on `src/data/columns.ts` and keeps each call's state in flat arrays (a cell is pool position × share); it opens an observation only to write out a full result. `rankVariants` does the arithmetic for both `computeIndex` and `rankScores` (scores alone, for history). `golden.test.ts` holds results byte for byte to `src/engine/fixtures/expected.json` (real data for one finished day, plus a small fixture with row shapes today's data lacks, and a lineup fit under a virtual clock). After changing the math on purpose, regenerate them with `npx tsx scripts/verify/engine-goldens.mts`, and check the diff is what you meant. The flow is drawn in `docs/ranking-logic.svg` (age filter, exclusions, measured share, Required gate, coverage floor, estimation, score). Regenerate the diagram when the gates change.

- **Scores are used as published.** Percent and fixed-scale scores are not rescaled (`FIXED_SCALES` covers snapshots without `normalization`). Nothing is stretched so the leader reads 100. Elo becomes win rate against the pool's median model. Other open-ended units go through a logistic around the pool median scaled by spread (USD in log space).
- **Cost means measured cost per task** (`aa-cost-per-task-index`, or a benchmark's `costUsd`). Never token price. `aa-price-blended` is `proxy: true`.
- **Effort matching** defaults to calibrated (`nearest` is a legacy alias). Exact results win. A missing effort uses the nearest measured effort, adjusted by the same model's ratio between those efforts on other benchmarks (ratio of means over the paired benchmarks). The ratio is capped at 4× either way and shrunk toward 1 by n / (n + 2) in log space, so one paired benchmark counts for a third of its size and 40 for nearly all of it. When the pairs say less effort scores higher (or more effort lower), there is no estimate: BullshitBench v2 scores Qwen 3.8 27B at 79 with no reasoning and 29 at max, and that ratio once put its no-reasoning Arena WebDev at 100. Without enough paired evidence the value stays missing. A maximum-effort score is never copied unchanged to a lower effort. Cost and speed are never effort-substituted. The donor value, source variant, multiplier and evidence are shown in the advanced Calculation settings; the main charts carry no estimate markers.
- **Strictness (0 to 100)** is the measured-coverage floor. A variant is ranked only when measured values (observed or effort-substituted; peer estimates never count) cover at least that share of the index's weight. 0 ranks anything with a value; 100 requires full coverage and disables inference. Strictness also sets the minimum number of effort comparisons, the allowed effort distance and the peer release window.
- **Required** benchmarks are hard per-benchmark gates. `optional` is a legacy field with no effect on ranking. `cutoff` survives for old URLs and derives strictness.
- **Missing values** above the floor are estimated from peers (release window, price tier) and marked, or the weights are renormalized when estimation is off. A peer estimate averages two guesses: the mix match (nearest models on the benchmarks in the mix, shifted by the average offset) and, for percent benchmarks, a panel match (models whose scores are closest as ratios across every measured percent benchmark they share, at least 8, scaled by the median ratio; reliability shares such as uptime are left out of that panel). Other models only; the target's own efforts never donate. Each estimate carries `donors` and an `estimateRange` (the donors' spread, never under 1.5 points), shown in the model detail and the bar tooltip. `scripts/verify/peer-backtest.mts` hides known scores and measures the miss: on the 2026-10-18 snapshot (168 hidden scores, 12 benchmarks) mean error fell from 7.5 to 6.5 points and 85% of hidden scores landed inside the range. Re-run it before changing the estimator. At strictness 50 and above, a model needs 2 measured benchmarks to seed estimates and peers need 2 shared benchmarks. The peer offset shrinks as `off/(n+1)`.
- **Versioned benchmarks** use `versionPolicy`: `fallback` (DeepSWE 1.1 falls back to 1) or `fresh` (AA index versions). A `fresh` version with `supersedes` also prompts a version notice to anyone whose own index weights the old id (`docs/pages-and-sharing.md`, "Benchmark version notices"), so set `supersedes` whenever a board replaces its last version.
- **Defaults:** strictness 50. `releasedAfter` undefined means models released in the six months before the snapshot date; an empty string (empty `after=` in the URL) means all time. Models with unknown release dates are never age-filtered.
- **Chart modes are independent.** `rankingVariants` defaults to `best`, `paretoVariants` to `all`. Compute the full variant set once, then call `selectVariants` per chart. `efforts` filters the cost, time and speed charts through `filterEfforts`.
- **The default view drops superseded versions.** Pages that show an index call `computeIndex(..., PAGE_VIEW)`. When the index has no `excludeModels` or `onlyModels` (nobody curated it), `supersededModelIds` (`src/engine/superseded.ts`) leaves out an older version of a line (same lab, same name apart from the version number, newer one no older by release date) none of whose efforts is on the cost frontier. A model with no measured cost cannot be on that frontier, so it is judged by score alone: it goes when a newer version scores at least as well. Under AA's v5 index only the models AA has run v5 on carry a cost, so most older versions are judged this way. Scores do not change, `result.autoHidden` lists them, the picker shows them unticked, and "All" is `excludeModels: []`, an explicit choice that turns the rule off. Internal callers (solver, optimizer, history) never pass `PAGE_VIEW`.
- **Scoring methods** (`IndexConfig.scoring`, `src/engine/scoring.ts`; Adam, 2026-11-19: an advanced option, out of the way). Unset is the weighted average described above, and that path runs none of this: `methodScorer` is only called when a method is set (`scoring.test.ts` mocks it to throw and ranks the default), and the golden outputs did not change. The method is chosen under Calculation settings in the mix editor (`ScoringMethodChoice.tsx`) and explained to readers at `/methods/scoring`. Both methods are applied after the gates, so every method ranks the same variants (same coverage floor, same Required gates, same exclusions); only `score` and the order change. Each scored row carries `method` (`MethodScore`: the method, the average it replaced, a 95% `range`, the fitted value and its standard error, and `used`, the mix benchmarks whose score counted). Both use every score the average uses (measured, effort-matched, calibrated) **except peer estimates**, which never enter a fit: a benchmark a model never ran is left to the fitted curve. The peer estimates still appear in `values`, since the radar and the model detail read them. Fits are deterministic (data-derived start, no randomness) and memoized on their cells (`cached`, the last 8), so a second ranking of the same index does not refit. A result scored by a method also carries `fit` (`ScoringFit`): each mix benchmark's slope, difficulty, chance floor and share, plus the straight line from the fit's scale to the score's (ECI-style only), which is what `/methods/scoring` draws its curves from; `scoring.test.ts` checks the curves reproduce every score.
  - **`irt`, IRT ability** (`irt.ts`, ported from the November 2026 lab). A two-parameter item response fit over the pool: expected score = floor + (1 - floor) × sigmoid(a × (ability - b)), by alternating Fisher scoring with weak priors, on the mix's benchmarks (scores measured at the variant's own effort) plus every percent benchmark outside the mix that 8 or more pool variants were measured on. A variant's score is then its ability from its mix scores alone, starting from its ability in that broad fit (prior sd 0.35, or the pool's sd 1 when the broad fit saw fewer than 4 of its scores). A weight is a share of the pull on ability: each benchmark's weight is divided by its Fisher information averaged over the pool, so a steep benchmark does not pull harder than its weight says. The score shown is the index score a model of that ability is expected to average on the mix (weights × expected scores), so it stays 0 to 100 and comparable with the average. The interval is a sandwich variance scaled by the fit's quasi-likelihood dispersion. Because the broad fit does not depend on the weights, dragging a slider refits nothing (about 150 ms for the first fit, then the average's cost). On a mix of one or two benchmarks the starting ability matters, so the order follows the benchmark less closely than the average does.
  - **`eci`, ECI-style** (`eci.ts`). After Epoch AI's Epoch Capabilities Index (epoch.ai/benchmarks/eci; methods at epoch.ai/data/eci-documentation/methodology and epoch.ai/publications/eci-bayesian-methodology, read 2026-11-19): expected score = sigmoid(slope × (capability - difficulty)), one capability per model, a difficulty and slope per benchmark, scores as 0 to 1 with chance taken out and clipped to 0.001..0.999, then a linear map to an open-ended scale. Where Priors differs: (1) it fits only the benchmarks in the mix, through Priors' usual 0 to 100 normalization, Elo included, where Epoch fits 50-odd benchmarks it chose and leaves Elo out; (2) weights: Epoch has none; here each benchmark's squared errors are multiplied by its share of the mix (mean 1), so equal weights are Epoch's loss; (3) the fit is Epoch's method until 2026-11-04, least squares with a ridge penalty of 0.1 / (M + 2B - 2) on every parameter and slopes held to 0.1..10, not the Bayesian sampler Epoch runs now, which is far too slow to run per slider tick (about 5 to 40 ms here per weight change); (4) the scale: Epoch pins Claude 3.5 Sonnet at 130 and GPT-5 at 150, and neither has scores on current benchmarks in Priors (Claude 3.5 Sonnet is not in the catalog), so capabilities are linked to Epoch's published index instead (`eciScale`, mean and sigma linking): over fitted variants that carry an `epoch-eci` row and have 4 mix scores (or all of a smaller mix), the mean and spread of the result equal those of Epoch's values. Fewer than 5 such variants (older snapshots, or a mix few of them took): the middle model reads 150 and one standard deviation of capability is 10 points. Ranks never depend on the scale; (5) inclusion is Priors' coverage floor, not Epoch's "four scores between 0.1 and 0.9"; (6) the interval is 95% from the weighted least-squares sandwich variance, where Epoch publishes 90% intervals from bootstrap or posterior samples. **`epoch-eci` is Epoch's own index as a benchmark and is not this method**; it only sets the scale and serves as a sanity check: `npx tsx scripts/verify/scoring-methods.mts` prints the top of each method, rank moves, fit times and the rank correlation with Epoch's index (0.975 over 24 variants on 2026-11-18, mean difference 1.4 ECI points; `scoring.test.ts` holds it above 0.9 on the golden day). A model with scores near zero everywhere gets a very low capability with a very wide interval, as Epoch notes of its own.
  - **What does not follow the method.** History (`computeHistory`) always uses the weighted average: a fit a day over 130 days is slow, and a fitted scale is relative to each day's models. The builder's `priors:mix` cookie drops the method, so the ranking flow and model pages keep the average. The onboarding fit, the rank-stability API and the default lineup never set it. The assistant's tools and the MCP tools rank with the index as stored, so they see the method's scores; the MCP settings name it (`scoring`, `scoringNote`).
  - **Bars and axes.** ECI-style scores sit near 150 to 175, so ranking bars start at 100 (`barShare`, `scoreBarBase`) and score axes fit the data (`methodScoreAxis` in `score-scale.ts`, given to charts through `ScoreAxisContext` and to share-card charts through `scatterSpec`). IRT ability keeps the 0 to 100 frame and its axis reads "Index score (IRT ability)".
- **The release-date chart places models the index cannot score.** AA runs its current evaluations only on recent models, so under the v5 index most older ones fall below the coverage floor (`excluded`, reason `coverage`) yet stay in the highlight menu. `progressEstimates` (`src/engine/progress-estimate.ts`) fits log(score) = a + b × AA Progress Index over the ranked efforts that have both (at least 8 pairs, R² ≥ 0.9, about 0.99 on the v5 index) and gives each such model an estimated score (`result.estimated`, `RankedVariant.scoreEstimate`); never above the highest paired Progress Index, never for a model the index scores or a benchmark the user required, and in a default view not for a superseded version unless highlighted. Only the release-date chart draws them, as rings labelled "est.", with the fit in the point card. Nothing ranks them, and the assistant's tools never see them.

## History

`/api/history` and the assistant's `index_history` call `computeHistory` (`src/lib/history.ts`): today's index on every snapshot date. It reads `data/snapshots/history.bin.gz` (`src/lib/history-archive.ts`), one columnar file with what a ranking reads from every dated snapshot: shared score rows plus a patch per date, walked forward through one `Columns`. Today's frame comes from the live snapshot. A date the file lacks is read from its dated snapshot, and with no usable file (absent, damaged, another `VERSION`) every date is, so the file costs nothing to lose but time. **Change `VERSION` when the format changes.** The file is generated, never committed: `build.ts` writes it after each scrape, `npm run build` writes it first from the checkout (`prebuild`; Vercel's `buildCommand` runs it too), and `scripts/ops/daily-scrape.sh` publishes it to `data-live`.

## Index configs and URLs

- `IndexConfig` is defined in the engine. `src/lib/url.ts` encodes it into one `i` query param per index: `?i=name|bench:w,...|req=|strict=|bars=|pareto=|est=|var=|effort=|labs=|ex=|only=|after=|tier=|score=`. Several `i` params mean several indices. `score=irt` or `score=eci` is the scoring method; absent (every link made before 2026-11-19, and every index on the default) is the weighted average, and any other value is ignored. Stored configs carry it as `scoring` under the same rule. `url.test.ts` pins old links to what the decoder returned before the field existed.
- Links are written through `prettyQuery`, which keeps `:`, `,` and `=` readable; both forms decode the same. `page=handle.id.key` marks the published page index a builder index was opened from. It is written only to the builder's own address and the owner's "Open in builder" links, rides along at runtime (`FromPage`), is trusted only with the key held in that tab's sessionStorage, and is never stored.
- Stored configs (profiles) are validated by `convex/validators.ts`. `IndexConfig` is asserted exactly equal to the validator at compile time, so adding a field on one side without the other fails `tsc`. Every write goes through `storableIndex()`, which drops transient keys. `src/lib/stored-index.test.ts` checks every config producer.
- Model visibility is stored as whichever is shorter: `excludeModels`, or an `onlyModels` allowlist once more than half the picker is hidden (new models then stay hidden). Hiding a model is the user's choice and reversible: excluded models can be re-checked in the chart-settings model picker.
- `src/lib/import.ts` is the zod schema for user and agent benchmark imports, and merges them into a snapshot.


## Benchmark pages

`/benchmarks` is a searchable directory (`src/components/benchmark/BenchmarkDirectory.tsx`): a category rail on the left, and rows whose values line up under labelled columns (top model, models, mixes, quality, stars), with a short-delay tooltip on each. A Columns switch (Overview, Quality factors) swaps top model, models and mixes for the six parts of the quality score (headroom, test set, recency, grading, new models, breadth; `QUALITY_FACTORS`), and the Sort menu can order by any of them. Search is loose (`searchBenchmarks(..., { loose: true })`): names outrank descriptions, every matched word counts before score, one typo in a name word is forgiven, and description words match by stem. The default order is recommended: quality (`qualityOf`, the onboarding's score) lifted by popularity: published pages with any index that weights it, and stars (`quality + 12 * log2(1 + uses) + 6 * log2(1 + stars)`, `src/lib/benchmark-recommended.ts`). Stars and page counts come from Convex, read at most once a minute per server instance (`src/lib/benchmark-community.ts`). Older versions and category splits are hidden until asked for, and searched always. `/benchmarks/methodology` explains quality and recommended; it reads `QUALITY_WEIGHTS`, `QUALITY_ADJUST` and `USE_LIFT`, so the page cannot drift from the math. The top model is the best score the publisher reports, older models included, never an estimate. Publisher icons load from DuckDuckGo's icon service, which the privacy page discloses.

`/models` is the model directory (`src/components/model/ModelDirectory.tsx`, data from `src/lib/model-directory.ts`), built on the benchmark directory's layout and styles: a lab rail, search over names, labs and aliases, and columns for Priors rank (the default index, General frontier, as the default ranking shows it, so superseded versions have a score but no rank), release date, benchmarks measured (distinct non-proxy benchmarks with a published result) and Artificial Analysis' blended API price. Every LLM with at least one result is listed; "Older versions" adds superseded ones (searches always include them) and "Open weights only" filters. It is linked from the site nav (Models), the footer and each model page's header (All models).

**Stars.** A signed-in person can star a benchmark, on its page or in the directory (`BenchmarkStar.tsx`, `convex/benchmarkStars.ts`: one row per account and benchmark in `benchmarkStars`, a running count per benchmark in `benchmarkStarCounts`, at most 500 stars an account). Counts are public; who starred what is returned only to that person. Signed out, the star is a link to sign-in that returns to the page. Stars lift the recommended order and are shown beside the quality score; they are not part of it.

**Benchmark facts** (`src/data/benchmark-facts.ts`). What a benchmark's results cannot tell us: whether the scored test set is public, partly private or private (`test`, with a one-sentence `testNote` and the `testUrl` that says so), whether its questions are replaced on a schedule (`refreshed`), its release date, how answers are graded, and whether labs report their own scores. A sub-board inherits its main board's facts (`factsOf`). The `RESEARCHED` table was written on 2026-11-19 by `scripts/research/benchmark-facts.mjs` from a research pass over all 357 main boards (cost, speed, usage and personality rows left out): one cheap agent per batch of 14 found each fact with a source and a quote, and a second checked the test-set and release-date claims against the cited page, setting anything it could not confirm to unknown. A claim neither pass was sure of is left out, which scores neutral. Corrections go in `OVERRIDES` in the same file, which win; a new benchmark gets an entry there in the same change that adds its scraper. The quality score reads these (docs/onboarding.md).

**Benchmark size** (`src/data/benchmark-size.ts`). How many tasks each leaderboard scores (votes for arena boards) and how many runs each is averaged over, researched 2026-11-23 with source URLs; `scripts/research/benchmark-size.mjs <dir> --write` regenerates the table from the research batches (low-confidence counts are dropped, so those stay unknown), and hand corrections go in `OVERRIDES`. The quality score's Size part reads it: samples = tasks × √runs (runs capped at 4, votes a tenth each), 10 samples score 0, 1,000 score 100, log scale, unknown 50.

**New-model speed** (`src/data/new-models.ts`). How quickly a benchmark scores new models, measured from Priors' own history: the snapshot build reads the history archive the last build wrote (`HistoryArchive.firstSeen()`: per benchmark, the first archived date each model had a published score), adds today's rows, and for every notable model released since the archive began (an LLM at least 20 benchmarks have scored) takes the days from its release to its first score on the benchmark. Full credit within 7 days, none after 60 or never, each model weighted by how many benchmarks test it; a model under 14 days old that the benchmark has not reached yet is left out, as is any model released before the benchmark was first seen. The result is `benchmark.newModels` (`of`, `added`, `medianDays`, `score`), absent with fewer than 3 such models or when the archive is missing (log line `NEW_MODELS`). It showed, for one, that DeepSWE 1.1 had scored no model released after early September.

`/benchmarks/<id>` is one benchmark's page (`src/app/benchmarks/[slug]`). Under the title it has a star and a one-line quality summary, and after the leaderboard a "Benchmark quality" panel (`QualityPanel.tsx`): the score, one line per part with its 0 to 100 bar, weight, points and the fact it rests on (the test-set line links its source), then the points added or taken away, then stars and pages using it. The server works this out from the full snapshot (`qualityView` in `src/lib/benchmark-page.ts`), since the page's trimmed snapshot cannot. The address is the benchmark id; looser forms such as `frontier-code-2` redirect to it (`src/lib/benchmark-slug.ts`, the current non-variant version wins). The page ranks models by that benchmark alone (`src/lib/benchmark-page.ts`) and only shows what the benchmark published: rows Priors estimated, fallbacks to an older version and calibrated routes from other benchmarks are stripped from its trimmed snapshot. Older versions and category splits are their own pages, linked from the Version and Category menus (`benchmarkRelatives`, following `supersedes` and `fallbackTo`).

Charts plot the benchmark's published value (dollars, Elo, percent) through `ScoreAxisContext` (`src/components/chart/score-axis.ts`) when higher is better; lower-is-better benchmarks keep the Priors scale. Everything else a source publishes is discovered from the observations (`src/lib/benchmark-metrics.ts`), not listed per source:
- per-task measurements (`steps`, `durationSec`, `outputTokens`) get their own score-vs-metric charts;
- every number under `details` (sub-scores, splits, counts, rubric rates) is a measure in "Score vs any published measure", and siblings under one parent (split by kind) form the Breakdown table;
- scraped `series` (Vending-Bench 2 money balance by day, from Andon's page bundle) and per-model number lists in details become line charts.
Run settings and interval bounds are skipped (the `SKIP` list). When the benchmark publishes cost per task, the cost chart uses it (`ViewOptions.costBenchmark`) with the same subscription adjustment as every other chart. The shared client snapshot drops `series` and most `details`; the benchmark page's own snapshot keeps them for its benchmark.
